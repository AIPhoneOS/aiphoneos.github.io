UX Open Questions

Design problems we haven't solved yet

We have architecture, security, and capability specs. We have zero visual designs. These are the UX problems that need answers before Phase 2.

Home Screen

  • What does the user see when they unlock the phone?
  • Is it a chat interface? A dashboard? A hybrid?
  • How do pinned apps appear? Grid? List? Cards?
  • Where is the text input vs voice input?
  • What happens when there are zero apps (first boot)?
  • How does it adapt between phone (portrait) and tablet (landscape)?

Voice Interaction

The product is "talk to your phone, get app." But we haven't designed the voice UX:

  • Activation: Always listening? Wake word? Push-to-talk button? Hardware button?
  • Feedback: How does the user know the phone is listening? Visual indicator? Sound?
  • Transcription display: Show real-time transcription? Or just show the response?
  • Noise handling: What happens in a noisy environment?
  • Privacy: If always listening, how do users trust that audio isn't being recorded/sent?

App Generation UX

  • What does the user see while the app is being generated? (Loading spinner? Progress? Preview?)
  • How long is acceptable? 5 seconds? 15? 30?
  • What if the AI needs to ask a clarifying question? How is that presented?
  • How does the permission approval flow look? (iOS-style popup? Full-screen card? Inline in chat?)
  • What does "edit this app" look like? Does the user see the app and chat side-by-side?

Incoming Calls & System Events

If our WebView is the entire UI, what happens when:

  • Phone call comes in: Who renders the incoming call screen? Our TWA dialer? AOSP's built-in call UI? What if the WebView has crashed?
  • Alarm goes off: How does it interrupt the current app?
  • Low battery warning: Who shows the notification?
  • System update: How is the user notified?
  • Crash recovery: If the home WebView crashes, what does the user see? How do they get back?

Likely answer: Keep AOSP's SystemUI for critical system events (calls, alarms, battery, crash recovery). Our TWA handles everything else. This means SystemUI is NOT stripped -- it's the safety net.

Notifications

  • Do we use Android's notification shade or build our own?
  • How do notifications from generated apps appear?
  • Status bar: do we show Android's status bar or replace it with our own?
  • Lock screen: what notifications show on the lock screen?

Multi-App Switching

  • User has 5 generated apps. How do they switch between them?
  • Swipe gesture? Button? Chat command ("go back to my tracker")?
  • Do apps run in the background or are they killed when not visible?
  • Is there a recents view? What does it look like?

Accessibility

  • How does a blind user interact with an AI-first phone? Screen reader support for generated apps?
  • Motor impairment: are all UI elements reachable with switch access?
  • Generated apps must produce accessible HTML -- how do we enforce this in the AI prompt?
  • Can the AI be instructed to generate apps optimized for specific accessibility needs?
  • Voice-first interaction is naturally accessible -- this could be an advantage

Internationalization

  • The AI chat needs to work in any language (Claude supports 100+ languages)
  • Generated app UI text -- does the AI generate in the user's language automatically?
  • RTL language support (Arabic, Hebrew)
  • System UI text: hardcoded English or localized?

Priority for Phase 1

Not everything needs to be solved now. Minimum viable UX for Phase 1 (emulator):

  1. Home screen: full-screen chat, text input, generated app cards
  2. App view: full-screen WebView with back button
  3. Keep AOSP SystemUI for calls, alarms, battery, status bar
  4. No voice yet (text only)
  5. No multi-app switching (one app at a time)
  6. English only
