OS Foundation Research

What can we actually build on, given Pixel 8 as the target device?

The Core Problem

Phone hardware drivers (camera ISP, cellular modem, GPU, BLE radio) only exist in two forms:

  • Android HALs -- binary blobs that plug into Android's Hardware Abstraction Layer
  • Mainline Linux drivers -- open source drivers in the upstream Linux kernel (incomplete for most phones)

Every non-Android phone OS must solve this: how do you talk to the hardware without Android?

Detailed Analysis

1. AOSP Minimal (Stripped Android)

Take AOSP source for Pixel 8. Remove all stock apps. Add your WebView runtime as the only visible process. Android framework runs invisibly underneath.

Pros:

  • 100% hardware support on Pixel 8 -- Google's own reference device, best-documented target
  • All drivers work: camera (including Tensor G3 ISP), cellular, BLE, NFC, GPS, WiFi, sensors, GPU
  • Security infrastructure included: verified boot, SELinux, dm-verity, full-disk encryption
  • OTA update mechanism built in (A/B partitions)
  • Massive documentation and community (LineageOS, GrapheneOS, CalyxOS all use AOSP)
  • Can strip apps in 1 day via build config -- no surgery needed

Cons:

  • 100GB source download, 2-4 hour builds, needs Linux (Docker on macOS)
  • Android framework runs underneath even if invisible -- ~1.5GB system image
  • Framework is a monolith -- stripping it beyond removing apps is months of work
  • Java/ART runtime is still there (for system services), even if no third-party apps use it
  • Feels philosophically wrong -- "building a new OS" on top of the OS you're trying to replace

2. Halium + Droidian (Debian with Android Drivers)

Halium keeps Android's kernel and HAL drivers but replaces everything above with standard Linux. Droidian is Debian running on Halium. You get apt-get, systemd, bash, and a normal Linux system with working phone hardware.

Pros:

  • Clean Linux system -- no Android framework, no ART, no Java
  • Standard Linux development: apt, systemd, bash, familiar tools
  • Small image (~500MB vs ~1.5GB for AOSP)
  • Full hardware support through Android drivers via libhybris bridge
  • Philosophically right -- it's a real Linux OS, not Android with a mask
  • Could run a minimal Wayland compositor + fullscreen Chromium as the entire UI

Cons:

  • No Pixel 8 port exists. Someone needs to create the Halium device adaptation. This is a significant project (weeks to months for an experienced porter).
  • Halium porting requires deep knowledge of Android kernel, device trees, and HAL interfaces
  • libhybris bridge adds complexity and potential instability
  • Smaller community than AOSP -- fewer resources, slower bug fixes
  • Camera support through Halium can be finicky (requires working with Android's camera HAL through droid-media)
  • We'd be doing TWO projects: porting Halium AND building our OS

3. Ubuntu Touch

Ubuntu + Halium. Same driver approach as Droidian but Ubuntu-based. More polished phone UX built in. But the newest supported Pixel is the 3a from 2019. UBports community is volunteer-driven with no plans for Pixel 8. Not viable.

4. postmarketOS (Mainline Linux)

Alpine Linux with mainline Linux kernel. No Android code at all. Pure open source. The dream.

Pros:

  • Truly minimal -- ~400MB image, fast boot
  • No Android anything -- pure Linux, pure open source
  • Standard Linux: apk, OpenRC, musl libc
  • Active community working on mainline drivers for many devices
  • Philosophically perfect -- a clean-slate Linux phone

Cons:

  • Camera barely works on Pixel 8. Tensor G3 ISP requires complex driver work. libcamera support is immature.
  • BLE is basic. Scanning works, advanced profiles and peripheral mode unlikely.
  • Cellular is partial. Calls may not work reliably. Data is better.
  • GPU acceleration partial -- no Vulkan, no WebGPU
  • Battery life significantly worse than Android
  • These hardware gaps will take months or years to fix upstream -- not in our control

5. SailfishOS

Jolla's Linux OS. Uses Halium for drivers. Has a nice UI. But parts are proprietary (the Silica UI framework), no Pixel 8 port, and Jolla's future is uncertain. Not viable.

6. Custom Linux (Buildroot/Yocto)

Build everything from scratch. Maximum control. But no phone drivers at all -- you'd need to port every driver manually. Camera: no. Cellular: no. BLE: no. GPU: no. This is a multi-year, multi-team project before you get a single phone call working. Not viable for a solo founder.

Conclusion

Use AOSP Minimal. Accept the bloat. Ship the product.

The Android framework running invisibly underneath is philosophically ugly. But it's the only path that gives you working camera + mic + BLE + cellular on Pixel 8 today, without months of porting work first.

The user never sees Android. They see your AI chat, your generated apps, your Capability Broker. What runs underneath is an implementation detail, not the product.

If this project succeeds and you build a team, you can:

  • Port Halium to Pixel 8 and migrate to a clean Linux base
  • Contribute to postmarketOS mainline drivers and switch when camera/BLE work
  • Build a custom AOSP fork that strips the framework more aggressively

But none of that matters until you prove that "talk to phone, get app" is something people want. Don't let the perfect foundation delay the product.

Future Migration Path

The architecture is designed so the foundation can change without rebuilding the product:

Today:     AOSP (stripped) → HALs → Kernel → Hardware
                ↑ your WebView sits here, talks to Capability Broker

Tomorrow:  Halium/Droidian → libhybris → HALs → Kernel → Hardware
                ↑ same WebView, same Broker, different plumbing

Someday:   postmarketOS → mainline drivers → Kernel → Hardware
                ↑ same WebView, same Broker, no Android at all

Your product code (the AI chat, the Capability Broker, the generated web apps) stays the same regardless of what's underneath. The foundation is swappable.
