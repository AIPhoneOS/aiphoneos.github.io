AI-Generated Code Liability

If a generated app leaks user data, crashes and loses information, or behaves maliciously, who is liable?

Current legal landscape (2026)

  • Courts will not accept "the AI did it" as a defense. Liability remains with the organization that deployed the code.
  • As the OS that generates and runs the code, we bear responsibility for the security model that contains it.
  • AI-generated code is not copyrightable in the US (no human authorship). Users own their data, not the generated code itself.
  • Due diligence matters: demonstrating that we sandbox, audit, and permission-gate generated code is our legal defense. "We ran static analysis, sandboxed the app, and required user approval for each capability" is a strong position.

Our mitigations

  • Generated code is always treated as untrusted (see Security Model)
  • 9-layer defense model: sandbox, broker, static analysis, CSP, network policy, permissions, audit, rollback, data sovereignty
  • User explicitly approves each capability before the app gets access
  • Full audit trail of every privileged action
  • Terms of service: generated apps are provided as-is, user accepts responsibility for what they ask the AI to build

Naming: "AIPhone"

Status: High risk. Requires professional trademark clearance before any public use.

  • "AIPhone" is phonetically and visually similar to "iPhone" (Apple's trademark)
  • Apple aggressively defends the "i" prefix and "Phone" suffix in their trademark portfolio
  • Even if legally distinct, consumer confusion is likely -- courts use a "likelihood of confusion" standard
  • The domain aiphone.online may also face challenges
  • Alternative names discussed: AetherOS, AIreOS, LLMware -- all require clearance

Action required: Engage a trademark attorney before any public launch, marketing, or investor materials.

Patent Landscape

Areas where patents may exist (requires professional patent search):

  • AI-generated applications: Microsoft, Google, and others have filed patents related to AI code generation
  • Web-based OS app model: Mozilla (Firefox OS), Google (ChromeOS/ARC), and others have prior art
  • Capability broker / permission systems: Android's permission model, iOS's entitlements, and WebKit's feature policy are prior art that may be patented
  • On-device AI inference: Google (Gemini Nano / AICore), Apple (Core ML / Neural Engine), Qualcomm (AI Engine) all have patents

Action required: Professional patent search before Phase 4 (public developer release). Prior art may be sufficient defense, but needs expert review.

Emergency Calling Regulations

If the OS is sold as a phone (not just a developer device), emergency calling requirements apply:

  • US (FCC): All phones sold must support 911 calling, including location services (E911)
  • EU: 112 emergency calling required
  • Australia: 000 emergency calling required, plus 112 (GSM standard)
  • These are non-negotiable for commercial phone sales

Our position

  • Phase 1-3: Developer/enthusiast device. Self-flashed. No commercial sale. Emergency calling works via AOSP telephony stack (unchanged).
  • Phase 5 (commercialization): Must verify emergency calling works correctly before any commercial distribution. Requires carrier testing.
  • Key risk: If our custom UI replaces the dialer, emergency calling must still work when the UI crashes or freezes. AOSP handles this at the system level, but we must not break it.

Open Source Licensing

  • AOSP: Apache 2.0 license -- we can build proprietary products on top
  • Linux kernel: GPLv2 -- kernel modifications must be open-sourced. Our code runs in userspace, not kernel, so this doesn't apply to our product code.
  • Chromium: BSD license -- we can modify and distribute freely
  • Our product code: License TBD. Could be open source (build community) or proprietary (protect IP).
