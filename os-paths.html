OS Build Paths Compared

Five ways to build the same product. Speed of development is the primary criterion.

The user experience is the same regardless of path: "talk to phone, get app." The question is how fast we can get there with working camera, microphone, internet, and bluetooth.

Detailed Analysis

A. Stock Android + Our Launcher App

Flash stock Android (or factory reset Pixel 8). Install AIPhoneHome as default launcher. Disable stock apps via ADB. Phone boots to our AI chat.

Dev speedFastest. Build an Android app in Android Studio. Standard APK development. You already know this workflow from your stores.
Hardware100% working. Stock Android drivers handle everything. Camera, BLE, mic, NFC, GPS, cellular -- all available via standard Android APIs.
Capability BrokerImplemented as Android code inside our app. WebView loads generated apps. Our Java/Kotlin code bridges WebView JS to Android system APIs. Full control over what web apps can access.
How it feelsUser unlocks phone, sees AI chat. Says "make me a timer." App appears. Indistinguishable from a custom OS to the user. Android is invisible underneath.

Pros:

  • Ship a working prototype in 1-2 days
  • All hardware works out of the box -- zero driver work
  • Standard Android app development -- massive ecosystem of docs, tools, libraries
  • Can distribute via Play Store or sideload APK
  • OTA updates handled by Google (system) and Play Store (our app)
  • Users don't need to flash anything -- just install an app
  • Can iterate daily, not weekly

Cons:

  • Can't remove stock Android apps entirely (can disable, not uninstall without root)
  • Android's launcher restrictions limit some home screen behaviors
  • Google could theoretically reject from Play Store (distribute via sideload as backup)
  • Status bar and navigation bar are still Android's (can hide but not fully replace)
  • Not a "real OS" -- it's an app pretending to be an OS
  • Can't modify system services (notification handling, boot sequence)
Verdict: The fastest path to "talk to phone, get app" with full hardware support. Gets the product in users' hands in days. The "it's just an app" concern is real but irrelevant until you have users who want more. Start here.

B. LineageOS + System App

Take LineageOS for Pixel 8 (community-maintained AOSP build). Add AIPhoneHome as a privileged system app. Remove stock launcher. Customize the build.

Dev speedModerate. Need to set up LineageOS build environment, but it's well-documented. Community handles device-specific drivers and updates.
Hardware100% working. LineageOS maintains Pixel 8 device trees with full hardware support.
Capability BrokerCan be a real Android system service with elevated permissions. Deeper integration than Path A. Can modify SystemUI, boot animation, init scripts.
How it feelsA real custom ROM. Boots directly to our home screen. No trace of stock Android. Custom boot logo, custom lock screen, custom everything visible.

Pros:

  • Full hardware support -- LineageOS community maintains Pixel 8 device trees
  • Can install our app as a privileged system app (deeper access than Path A)
  • Can strip stock apps completely (not just disable)
  • Can modify SystemUI, boot animation, default settings
  • Community handles kernel updates, security patches, driver maintenance
  • Smaller build than full AOSP (only builds what's needed for the device)
  • Can add custom system services (Capability Broker as a real system service)
  • No Google dependency -- LineageOS ships without GMS by default

Cons:

  • Need to learn the LineageOS build system (documented but takes a few days)
  • Builds require Linux (Docker on macOS)
  • Still carries Android framework, ART runtime, and other bloat we don't need
  • Dependent on LineageOS community for device tree updates
  • Users must unlock bootloader and flash -- limits audience to enthusiasts
  • Slower iteration than Path A (rebuild + reflash vs just update APK)
Verdict: The best middle ground. Real custom ROM with full hardware support, without the pain of maintaining your own AOSP fork. Graduate to this after Path A proves the experience works.

C. Full AOSP Build

Download AOSP source (~100GB). Configure for Pixel 8. Build everything from scratch. Full control over every system component.

Dev speedSlowest. Days to set up build env, hours to sync, hours to compile. Steep learning curve for system-level Android.
Hardware100% working (Pixel 8 is a Google reference device with full AOSP support).
Capability BrokerCan be anything. Custom system service, custom framework APIs, custom SELinux policies. Total architectural freedom.
How it feelsA completely independent OS. Your name on the boot screen. Your runtime. Your rules.

Pros:

  • Total control -- can strip ART, replace Android framework, add kernel modules
  • Can define entirely new system services and APIs
  • Can optimize for size/speed by removing unused AOSP components
  • No dependency on any community project
  • The "real" version of the OS -- everything else is a stepping stone to this
  • Can implement custom Chromium Content Shell as the TWA runtime

Cons:

  • 100GB+ source download, 150GB+ build output, 2-4 hour builds
  • Requires Linux (Docker on macOS adds friction and build time)
  • YOU maintain device trees, kernel patches, security updates, driver compatibility
  • System-level Android is extremely specialized -- steep learning curve
  • Months before it's stable enough for daily use
  • Solo founder maintaining a full OS fork is unsustainable long-term
  • Every AOSP security patch must be manually merged
Verdict: The ultimate destination if the product succeeds and you raise money / build a team. Not where a solo founder should start. The risk: you spend 6 months on build infrastructure and never get to the product. Phase 3+ after you have users.

D. postmarketOS (Mainline Linux)

Alpine Linux-based phone OS that runs mainline Linux kernel. Skip Android entirely. Use Phosh or Plasma Mobile as the shell, or build your own.

Dev speedFast for the OS layer (standard Linux development), slow for hardware.
HardwarePartial. Pixel 8 support exists but is immature. Camera usually doesn't work well. Cellular is partial. BLE is basic.
Capability BrokerStandard Linux userspace. Can use any approach -- D-Bus services, custom daemons, whatever you want. No Android framework overhead.
How it feelsA Linux phone. Different from Android. Lighter, simpler, but rougher.

Pros:

  • No Android bloat at all -- clean Linux system, tiny image
  • Standard Linux development -- familiar tools (apt, systemd, bash)
  • Can build the entire UI shell from scratch in web tech (Electron/WebView + custom WM)
  • Active community (Pine64, Purism Librem 5 users)
  • Truly independent from Google -- even the kernel is mainline, not Android's fork
  • Much smaller codebase to understand and modify

Cons:

  • Camera barely works on Pixel 8 -- libcamera support for Tensor G3 ISP is immature
  • Bluetooth/BLE is basic -- scanning works, advanced profiles may not
  • Cellular data works but calling/SMS can be unreliable
  • GPU acceleration may be partial (no Vulkan/WebGPU)
  • No NFC
  • Battery life is significantly worse than Android
  • Small community -- fewer resources, slower fixes for hardware issues
  • You'd be a phone OS project AND a hardware enablement project -- two full-time jobs
Verdict: Philosophically appealing (pure Linux, no Google) but fails the hardware requirement. Camera barely works, BLE is basic, battery life is poor. Only viable if you can accept broken camera and partial BLE for months while upstream catches up. Not recommended for this project.

E. Custom Linux (Buildroot/Yocto)

Build a minimal Linux system from scratch using Buildroot or Yocto. Custom kernel config, custom rootfs, custom everything. Maximum control, maximum work.

Dev speedExtremely slow. You're building an OS from the ground up. Months before basic phone functionality works.
HardwareMinimal. You'd need to port drivers from Android's kernel fork manually. Camera, cellular, BLE -- all require significant porting work.
Capability BrokerTotal freedom. But you're also building everything else -- init system, display server, audio, networking.
How it feelsAn embedded system that happens to be on a phone. Raw, minimal, probably broken.

Pros:

  • Absolute minimal system -- tiny image, fast boot, zero bloat
  • Total architectural freedom from day one
  • No dependency on any external project

Cons:

  • Camera: No. Tensor G3 ISP drivers are Android-specific. Porting is a multi-month project.
  • Bluetooth: No. Requires Android's Bluetooth HAL or a complete rewrite.
  • Cellular: No. Qualcomm/Samsung baseband requires Android's RIL (Radio Interface Layer).
  • GPU: No. Mali/Adreno drivers are Android-specific.
  • You're building an entire OS from scratch. This is a 50-person, multi-year project.
  • No community to help. You're alone.
Verdict: Do not do this. You'd spend years getting basic hardware working before you ever touch the AI app generation that is the actual product. This is how projects die.

Recommended Sequence

WhenPathWhy
NowA. Stock Android + LauncherWorking prototype with full hardware in days. Validate the experience. Iterate fast.
When experience is provenB. LineageOS + System AppGraduate to a real custom ROM. Strip stock apps. Add system-level Capability Broker. Still has community hardware support.
When you have users + teamC. Full AOSP BuildFork AOSP. Own the entire stack. Build the TWA runtime properly. This is the end-state OS.

Skip D and E entirely. They fail the hardware requirement and add months of work that has nothing to do with your product.

The key insight: Paths A, B, and C all deliver the same user experience -- "talk to phone, get app." The user doesn't know or care whether the Capability Broker is an Android app, a system service, or a custom framework API. They just know their phone creates apps. Start with the path that gets them there fastest.
