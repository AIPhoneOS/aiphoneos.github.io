Why LiteRT-LM Wins

1. Speed: 52 tokens/sec on Android GPU

LiteRT-LM uses OpenCL for GPU compute on Android — not Vulkan. OpenCL has better driver support on many mobile GPUs including Imagination (Pixel 8). Google benchmarked 52 t/s decode speed on Android GPU. llama.cpp Vulkan on the same class of hardware is ~15-25 t/s and untested on Imagination GPUs specifically.

At 52 t/s, a 2000-token app (~complete HTML/CSS/JS) generates in ~38 seconds. At 15 t/s (llama.cpp), it would take ~133 seconds. That's the difference between "fast" and "unusable."

2. GPU inference that doesn't kill the UI

LiteRT-LM is designed for mobile. It manages GPU resource sharing with the Android rendering pipeline. llama.cpp's Vulkan backend was built for desktop GPUs where the display compositor isn't competing for the same hardware.

3. KV Cache and Session Management — Built In

For multi-turn conversation ("make me a timer" → "now add a lap feature"), the model needs to remember context. LiteRT-LM handles KV cache persistence, session state, and prompt caching automatically. With llama.cpp, we'd build all of this ourselves.

4. Supports All Our Models

LiteRT-LM supports Gemma, Llama, Phi-4, and Qwen. These are exactly our chosen models (Gemma 1B for routing, Phi-4 Mini for generation). No model conversion needed for the standard ones.

5. No GMS Required

Unlike MediaPipe LLM's AICore path (which needs Google Play Services), LiteRT-LM runs standalone. Perfect for our GrapheneOS base with no Google services.

6. Google Built It for This Exact Hardware

LiteRT-LM is built by the same company that makes the Tensor G3 chip. The GPU (OpenCL) and NPU optimizations are tested on Pixel hardware. No one knows the Imagination GPU driver quirks better than Google.

The LLMaaS Architecture Pattern

Academic research (LLM as a System Service on Mobile Devices) formalizes exactly what we're building:

Key Concepts

  • Single model instance: One copy of LLM weights in memory, shared across all apps. Not one model per app.
  • OS-level request queue: All inference requests (from home screen, from generated apps via aiphone.ai.ask(), from intent routing) go through one queue. The OS prioritizes and schedules.
  • KV cache sharing: If two apps ask similar questions, the KV cache from the first can partially serve the second. Saves compute and energy.
  • Per-app KV cache isolation: Each app's conversation context is isolated for privacy, but the model weights are shared.
  • Energy-aware batching: If multiple requests arrive within a short window, batch them for GPU efficiency rather than running sequentially.
  • Memory pressure handling: When RAM is low, compress KV cache (quantize to lower precision) rather than evicting it entirely. Faster to decompress than to recompute.

P0 requests preempt everything. If the user types while an app is generating, intent routing runs immediately and generation pauses momentarily.

Thermal Management

  • Monitor: AiService watches ThermalManager for device temperature.
  • Throttle: At thermal level MODERATE, reduce generation speed (lower batch size).
  • Pause: At thermal level SEVERE, pause local generation entirely. Queue requests for cloud fallback.
  • Resume: When temperature drops, resume local generation from where it paused.

Revised Decision

LiteRT-LM replaces llama.cpp as inference engine

  • Runtime: LiteRT-LM (C++ core, Java API, Apache 2.0)
  • GPU backend: OpenCL — 52 t/s proven on Android, designed to coexist with UI rendering
  • NPU backend: Built-in NPU support for Tensor G3 TPU
  • Models: Gemma 1B (router) + Phi-4 Mini (generator) — both supported natively
  • Architecture: LLMaaS pattern — single model instance, OS-level request queue, per-app KV cache
  • CPU: Reserved for UI only. Never used for inference.
