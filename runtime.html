Runtime Decision

V8 vs Chromium vs WebKit vs Servo vs Canvas -- how do web apps actually run?

The Question

If web apps are the only app format, what engine runs them? "A WebView" is not a complete answer. The runtime choice affects performance, capability, size, and what AI can generate.

What V8 Actually Is

V8 is Google's JavaScript engine. It compiles JS to native machine code. It's fast and well-maintained. But V8 alone cannot render HTML or CSS. It executes JavaScript, nothing more. To display a web page, you also need:

  • An HTML parser
  • A CSS layout engine
  • A rendering/painting engine
  • A DOM implementation
  • Networking, media playback, etc.

V8 is the engine. Chromium is the car.

Options Evaluated

RuntimeWhat it isProCon
Chromium Content Shell V8 + Blink renderer. Chromium stripped to its rendering core. No browser UI. Most capable web engine. Full WebGPU. Best web API coverage. AI generates standard HTML/CSS/JS. Large (~150MB). Comes from Google. Complex codebase.
Android System WebView AOSP's built-in Chromium wrapper. Updated via system. Already in AOSP. Well-maintained. Standard. Designed for embedding in apps, not as an OS runtime. Limited customization.
WebKit Safari's engine. Apple-maintained. Lighter than Chromium. Battle-tested. WebGPU lagging. Fewer web APIs than Chromium. Apple-controlled priorities.
Servo Mozilla/Linux Foundation experimental engine. Written in Rust. Modern, memory-safe, parallel rendering. Lighter. Not production-ready. Incomplete web API coverage. Small team.
V8 + custom renderer V8 for JS, build our own layout/rendering engine. Maximum control. Could optimize for AI-generated apps. Building a rendering engine is a multi-year, multi-team project. Browsers are among the most complex software ever built.
V8 + Canvas/Skia Skip HTML/CSS. Render everything to a GPU canvas (like Flutter). High performance. Direct GPU access. AI is much worse at generating canvas-based UIs than HTML/CSS. Kills the core advantage of web tech.

Why Chromium Content Shell Wins

  1. AI generates HTML/CSS/JS. That's what LLMs are best at. Any runtime that doesn't render standard HTML kills the app generation thesis.
  2. WebGPU. On-device AI inference through the web runtime. Chromium has the best WebGPU support.
  3. Web API coverage. Service Workers (offline), IndexedDB, Canvas, WebGL, MediaDevices, Intersection Observer -- Chromium supports more web APIs than any other engine.
  4. Already in AOSP. System WebView is Chromium-based. We don't need to add a new engine -- we strip the existing one to its core.

The "No Frameworks" Principle

The OS itself is built with zero JavaScript frameworks. No React. No Vue. No Angular. No Capacitor. No Ionic. No Electron.

  • System UI: plain HTML + vanilla JS + CSS
  • Generated apps: plain HTML + vanilla JS + CSS
  • Capability Broker bridge: plain Java talking to plain JS via WebView interface

Frameworks add layers. Layers add latency, bugs, dependencies, and upgrade treadmills. The AI generates plain web code. The OS runs plain web code. No middlemen.
